# OpsFlow SRS — 인증·권한 관리 (AUTH)
문서 버전: 0.1 | 작성일: 2026-10-13 | 상태: 초안
(Claude.ai 대화에서 작성됨, 2026-10-14 저장소에 뒤늦게 저장)

## 이번 영역에서 결정한 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 인증 방식 | **JWT (Access Token 15분 + Refresh Token 7일, httpOnly 쿠키)** | SPA(React) + REST API 구조에 가장 표준적. 세션 스토어 없이 수평 확장 쉬움. Access Token은 메모리에만 보관해 XSS 노출 최소화 |
| 비밀번호 해싱 | **bcrypt (cost factor 12)** | 업계 표준, NestJS 생태계 지원 풍부, 별도 인프라 불필요 |
| 멀티테넌시 구현 방식 | **Row-level (단일 DB, 모든 테이블에 `organization_id` 컬럼)** | 개인 프로젝트 규모에서 schema-per-tenant는 과도한 복잡도 |
| 조직 초대 방식 | **이메일 초대 링크 (토큰 기반, 만료시간 포함)** | 가장 일반적인 B2B SaaS 온보딩 패턴 |
| 계정 생성 경로 | **공개 회원가입 없음. 반드시 조직 초대(AUTH-005)를 통해서만 계정이 만들어짐** | B2B 내부 툴 특성상 아무나 가입하면 안 됨. "role/organization_id는 사용자가 아니라 초대장이 결정" |

> ⚠️ **가장 중요한 차이점**: 이 프로젝트에는 `POST /auth/signup` 같은 공개 회원가입 엔드포인트가 없습니다. 계정은 오직 AUTH-005(조직 구성원 초대)를 통해서만 생성됩니다 — Admin이 이메일+역할로 초대 → 초대 토큰으로 가입 시 해당 조직·역할이 자동 부여됨. "누구나 role 없이 가입하면 MEMBER로 만들어주는" 공개 가입 플로우는 설계에 없던 내용입니다.

## 공통 전제
- 모든 보호된 API는 Access Token 검증 + 역할(RBAC) + `organization_id` 소유권을 함께 확인
- 인증 실패 401, 인가 실패 403, 리소스 없음/타 조직 리소스 404로 구분

---

## AUTH-001. 로그인
| 항목 | 내용 |
|---|---|
| 사용자 | 전체 (미인증 상태) |
| 입력 | 이메일, 비밀번호 |
| 처리 | 자격 증명 검증 → Access Token(응답 body) + **Refresh Token(httpOnly 쿠키)** 발급 |

**예외 처리**
- 존재하지 않는 이메일 / 틀린 비밀번호 → 401, **동일한 오류 메시지**로 통일 (계정 존재 여부 유추 방지)
- 연속 실패 시도 과다 → 429 (brute-force 방지)
- 비활성화된 계정 로그인 시도 → 403

**수용 기준**
- [ ] 올바른 자격 증명으로 로그인하면 Access/Refresh Token이 발급된다
- [ ] 틀린 비밀번호와 존재하지 않는 이메일은 동일한 오류 메시지를 반환한다
- [ ] 일정 횟수 이상 연속 실패 시 일시적으로 차단된다

## AUTH-002. 로그아웃
| 항목 | 내용 |
|---|---|
| 처리 | Refresh Token 무효화(서버 측 blacklist 또는 DB 레코드 삭제), 쿠키 제거 |

**수용 기준**
- [ ] 로그아웃 후 기존 Refresh Token으로 재발급 시도 시 401을 반환한다

## AUTH-003. 토큰 재발급
| 항목 | 내용 |
|---|---|
| 처리 | 유효한 Refresh Token으로 새 Access Token 발급 |

**예외 처리**
- 만료/무효화된 Refresh Token → 401, 재로그인 필요

**수용 기준**
- [ ] Access Token 만료 후에도 유효한 Refresh Token이 있으면 재로그인 없이 세션이 유지된다
- [ ] Refresh Token도 만료되면 재로그인을 요구한다

## AUTH-004. RBAC 공통 인가 미들웨어
| 항목 | 내용 |
|---|---|
| 검증 순서 | ① 토큰 유효성 → ② 역할이 해당 액션을 수행할 수 있는가 → ③ 리소스가 본인 조직 소속인가 → ④ (해당 시) 리소스 소유권/담당자 관계 |

**설계 원칙**
- 프론트엔드 버튼 숨김은 보조 수단일 뿐, 모든 검증은 백엔드 공통 가드(NestJS Guard)에서 수행

**수용 기준**
- [ ] 역할 조건을 만족하지 못하면 어떤 엔드포인트든 일관되게 403을 반환한다
- [ ] 다른 조직 리소스에 대한 모든 접근은 일관되게 404를 반환한다
- [ ] 새 엔드포인트 추가 시 개별 권한 로직 없이 기존 가드를 재사용할 수 있다

## AUTH-005. 조직 구성원 초대 (= 사실상 유일한 계정 생성 경로)
| 항목 | 내용 |
|---|---|
| 사용자 | Admin |
| 입력 | 초대 대상 이메일, 부여할 역할(Member/Manager) |
| 처리 | 초대 토큰 생성 + 이메일 발송 → 토큰 유효기간 내 가입 시 해당 조직·역할로 계정 생성 |

**예외 처리**
- 이미 가입된 이메일 재초대 시도 → 409 (MVP는 1사용자 1조직으로 단순화)
- Manager/Member의 초대 시도 → 403 (Admin 전용)
- 만료된 초대 토큰으로 가입 시도 → 400

**수용 기준**
- [ ] Admin만 구성원을 초대할 수 있다
- [ ] 초대 토큰은 유효기간이 지나면 사용할 수 없다
- [ ] 초대받은 사용자는 가입 즉시 지정된 조직·역할로 활성화된다

## AUTH-006. 역할 변경
| 항목 | 내용 |
|---|---|
| 사용자 | Admin |
| 처리 | 조직 내 구성원의 역할(Member ↔ Manager ↔ Admin) 변경 |

**예외 처리**
- Admin 본인이 스스로를 강등하여 조직에 Admin이 0명이 되는 경우 → 409 (조직은 항상 최소 1명의 Admin 보유)
- Manager/Member의 역할 변경 시도 → 403

**수용 기준**
- [ ] Admin만 역할을 변경할 수 있다
- [ ] 조직의 마지막 Admin은 스스로를 강등할 수 없다
- [ ] 역할 변경 이력이 감사 로그에 기록된다
